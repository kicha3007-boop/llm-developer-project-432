# ADR 0002. Миграции схемы: SQL-файлы и свой раннер

Статус: принято.

## Контекст

В практике темы таблица создавалась запросом `CREATE TABLE IF NOT EXISTS` при подключении. Дальше
таблиц пять (`schema_migrations`, `jobs`, `documents`, `chunks`, `llm_calls`), появляются индексы
HNSW и GIN, генерируемая колонка `tsvector`, частичный индекс. Схему надо уметь менять, а не только
создавать.

## Решение

Обычные SQL-файлы `db/migrations/NNNN_name.sql` и раннер `app/core/migrate.py`
(`python -m app.core.migrate`, `make migrate`):

- файлы применяются по порядку версий, каждый — в своей транзакции вместе с записью версии;
- применённые версии отмечаются в таблице `schema_migrations`, её создаёт первая миграция
  (вместе с `CREATE EXTENSION vector`);
- повторный запуск ничего не применяет и печатает «Новых миграций нет»;
- `pg_advisory_lock` не даёт двум одновременным запускам применить одно и то же;
- имя файла не по шаблону и две миграции с одной версией — ошибка до применения.

Тест `tests/test_infra.py::test_migrate_from_scratch_then_noop` создаёт чистую базу, применяет все
миграции и проверяет, что второй прогон пустой.

## Альтернатива

Alembic: даёт автогенерацию и откаты, но прячет SQL за прослойкой, а всё интересное в проекте
(`vector(768)`, `hnsw (embedding vector_cosine_ops)`, `GENERATED ALWAYS AS (to_tsvector(...))`,
оконные функции) всё равно пишется руками на SQL. Для пяти таблиц раннер в шестьдесят строк проще.

## Компромиссы

Нет автоматических откатов: исправление — новой миграцией вперёд. Размерность вектора (768) зашита
в миграции; смена модели эмбеддингов с другой размерностью — новая миграция и `make reindex`
(эмбеддер при загрузке сверяет размерность модели с настройкой и падает с понятной ошибкой).
