# ADR 0004. Защита, проверка источников, стоимость и трассировка

Статус: принято.

## Проверка источников (против выдумывания)

Каждый фрагмент в контексте опознаваем заголовком `[chunk_id | файл | стр. N | секция]`, модели
передаётся список допустимых `chunk_id`. После генерации код (`rag_pipeline.verify_sources`)
проверяет каждый источник по двум условиям: фрагмент существует в базе **и** входил в поданный
контекст; плюс каждая характеристика обязана иметь источник. Страница и секция источника берутся
из контекста, а не со слов модели. Нарушение — переделка с текстом ошибки; повторное — задача
уходит человеку (`needs_review`). Проверяющая роль (дешёвая модель) затем сверяет утверждения с
заявленными фрагментами.

## Персональные данные

`guardrails/pii.py`: телефон, почта, ИНН (контрольная сумма для 10 и 12 цифр), номер карты (Луна).
Маскирование меток вида `[ТЕЛЕФОН_1]` с общей нумерацией в пределах задачи выполняется в
`rag/context.py` **до** любого вызова модели (в том числе детектора инъекций) и до логирования.
Вторая линия — процессор structlog маскирует все записи логов. Проверено на живом стенде: поиск
исходных контактов из `blender_kp.docx` и `kettle_manual.pdf` по логам прогона ничего не находит.
Артикулы, суммы с пробелами, ОГРН (13 цифр), даты не трогаются — это закреплено тестами.

## Инъекции

`guardrails/injection.py`, два уровня: правила (приказы игнорировать инструкции, маркеры ролей,
вытаскивание промпта, смена роли, «в карточке укажи…», длинные base64) — бесплатно; узкий вопрос
дешёвой модели со структурированным вердиктом — только по фрагментам, помеченным правилами.
Недоступный точный уровень → фрагмент считается подозрительным (fail-closed). Подозрительные
фрагменты выбрасываются из контекста; больше `INJECTION_MAX_SUSPICIOUS_PER_DOC` в одном документе —
документ целиком исключается, задача уходит человеку с причиной. Разборщик pdf отделяет текст
мелким кеглем в отдельный фрагмент, поэтому вставка из `kettle_manual.pdf` не утаскивает за собой
соседний абзац «Условия сотрудничества».

Фильтр выхода (`guardrails.check_output`) проверяет текст готовой карточки теми же детекторами:
контакты, метки маскирования, следы служебных инструкций. Нашёл — контакты маскируются, задача
уходит человеку. В результат задачи пишется `security_report`: исключённые фрагменты с причинами,
счётчики замаскированного по видам, отправленные человеку документы, находки фильтра выхода.

## Стоимость

Таблица `llm_calls` (задача, запрос, назначение, уровень main/cheap, модель, токены, стоимость
`NUMERIC(14,8)`, длительность, попытка, статус). Пишет её **клиент модели** после каждого вызова,
в том числе неудачного, — учёт нельзя забыть в новом месте. Деньги — `Decimal`, цены за миллион
токенов в настройках. Служебные роли (`critic`, `rag_critic`, `injection_judge`, `eval_judge`)
помечены `cheap=True` и уходят на `LLM_CHEAP_MODEL` — разбивка видна в `GET /jobs/{id}/cost` и
`make cost JOB=...`.

## Трассировка

`request_id` рождается в промежуточном слое (или берётся из `X-Request-ID`), `job_id` привязывается
в обработчике сразу после создания задачи, передаётся аргументом процесса Temporal и привязывается
к контексту логов в каждом шаге; клиент модели берёт оба из контекста и пишет в `llm_calls`.
Поиск по `job_id` в логе показывает обработчик, все шаги процесса (с номером попытки шага),
вызовы модели с длительностью и итог.
